# 양파 전문 쇼핑몰 프로젝트 기획안

## 1. 프로젝트 개요

### 프로젝트명
**ONION MALL**  
가칭

### 프로젝트 기간
**10일**

### 프로젝트 형태
양파 농장 또는 양파 유통 회사가 직접 운영하는 **단일 판매자 온라인 쇼핑몰**

### 프로젝트 소개

ONION MALL은 하나의 양파 농장 또는 양파 유통 회사가 직접 상품을 등록하고 판매하는 자사몰 형태의 온라인 쇼핑몰이다.

고객은 상품을 검색하고 조회한 뒤 장바구니에 담아 주문·결제할 수 있으며, 운영자는 상품 등록, 재고 관리, 주문 관리, 고객 문의 대응 등의 기능을 사용할 수 있다.

본 프로젝트는 단순한 쇼핑몰 CRUD 구현에 그치지 않고, 서비스 이용자가 증가하면서 발생할 수 있는 **데이터 정합성 문제와 조회 성능 문제를 직접 재현하고 개선하는 것**을 목표로 한다.

특히 다음 문제를 주요 기술 과제로 다룬다.

- 한정된 재고에 주문 요청이 동시에 몰렸을 때 초과 판매를 어떻게 방지할 것인가?
- 여러 사용자가 동시에 상품에 좋아요를 눌렀을 때 증가 값이 유실되지 않도록 어떻게 처리할 것인가?
- 동일한 결제 요청이 여러 번 전달되었을 때 중복 결제를 어떻게 방지할 것인가?
- 상품과 주문의 검색 조건이 다양해질 때 조회 로직을 어떻게 유연하게 구성할 것인가?
- 좋아요가 많은 상품을 인기순으로 효율적으로 조회할 수 있는가?
- 주문 데이터가 증가했을 때 검색 및 정렬 성능을 어떻게 개선할 것인가?
- 동일 상품 및 인기 상품 목록에 반복 조회가 집중될 때 데이터베이스 부하를 어떻게 줄일 것인가?

# 2. 프로젝트 기획 배경

온라인 쇼핑몰의 기본 흐름은 다음과 같다.

```text
상품 검색
→ 상품 조회
→ 장바구니
→ 주문
→ 결제
```

데이터와 요청량이 적을 때는 단순 CRUD만으로도 정상적으로 동작할 수 있다.

하지만 서비스 이용자가 증가하면 여러 문제가 발생한다.

예를 들어 양파 재고가 100개 남아 있는데 1,000명의 사용자가 동시에 주문한다면 여러 요청이 같은 재고를 조회하면서 실제 재고보다 많은 주문이 성공할 수 있다.

또한 좋아요가 0인 상품에 100명의 사용자가 동시에 좋아요를 누른다면 여러 트랜잭션이 동일한 값을 읽고 수정하면서 증가분이 유실되는 Lost Update가 발생할 수 있다.

조회 측면에서도 주문 데이터가 수십만 건 이상 쌓이면 조건 검색이 느려질 수 있고, 인기 상품이나 상품 상세 페이지에 조회가 집중되면 동일 데이터를 조회하기 위해 데이터베이스에 반복적으로 접근하게 된다.

따라서 본 프로젝트에서는 다음 두 가지 방향을 중심으로 설계한다.

## 데이터 정합성

```text
재고
좋아요
결제
```

## 조회 및 성능

```text
QueryDSL
인기순 조회
복합 인덱스
Redis Cache
```

# 3. 프로젝트 핵심 목표

> **동시 요청이 발생하는 상황에서도 거래 데이터의 정합성을 보장하고, 데이터와 조회 트래픽이 증가했을 때 검색·정렬·반복 조회 성능을 개선한다.**

```text

   ↓
문제 상황 재현
   ↓
측정
   ↓
원인 분석
   ↓
해결 방법 적용
   ↓
재측정
```

# 4. 서비스 컨셉

ONION MALL은 여러 판매자가 입점하는 마켓플레이스가 아니다.

하나의 양파 회사가 자신의 상품을 직접 판매하고 운영하는 **단일 브랜드 자사몰**이다.

판매자와 운영자를 별도로 구분하지 않는다.

```text
양파 회사

사장 / 직원
    ↓
  ADMIN


일반 고객
    ↓
 CUSTOMER
```

# 9. 상품 검색 - QueryDSL

상품 목록에서는 여러 검색 조건과 정렬 방식을 지원한다.

## 검색 조건

- 상품명

- 최대 가격
- 상품 상태

## 정렬 조건

- 최신순
- 가격 낮은순
- 가격 높은순
- 인기순

예:

```http
GET /api/products/search
?keyword=햇양파
&minPrice=10000
&maxPrice=30000
&status=SELLING
&sort=POPULAR
&page=1
```

검색 조건은 선택적으로 조합할 수 있다.

```text
상품명

가격 + 상태

상품명 + 가격 + 상태

조건 없음
```

조건별 Repository 메서드나 JPQL을 계속 작성하지 않고 **QueryDSL을 사용하여 동적으로 검색 조건을 구성한다.**

### ProductSearchCondition

```text
keyword
minPrice
maxPrice
status
```

### ProductSort

```text
LATEST
PRICE_ASC
PRICE_DESC
POPULAR
```

### QueryDSL 적용 목적

> 다양한 검색 조건과 정렬 조건을 하나의 검색 API에서 유연하게 조합하기 위해 사용한다.

# 10. 인기 상품 조회

사용자는 좋아요가 많은 상품을 인기순으로 조회할 수 있다.

10일 프로젝트에서는 복잡한 인기 점수 알고리즘을 만들지 않고 **좋아요 수를 인기 기준으로 사용한다.**

## 인기순 기준

```text
1순위 : likeCount DESC
2순위 : createdAt DESC
```

예:

```text
1. 햇양파 5kg       좋아요 824
2. 자색양파 3kg     좋아요 521
3. 못난이양파 10kg  좋아요 312
```

API 예:

```http
GET /api/products?sort=POPULAR&page=1
```

또는 메인 화면에서는 상위 상품만 제공할 수 있다.

```http
GET /api/products/popular?size=10
```

## 인기순 조회 목적

- 사용자에게 반응이 좋은 상품을 우선 노출한다.
- 좋아요 기능을 단순 사용자 상호작용이 아니라 실제 상품 정렬 기능과 연결한다.
- 반복적으로 조회되는 인기 상품 목록을 Redis Cache 적용 대상으로 활용할 수 있다.

# 12. 좋아요 동시성 문제

## 문제 상황

초기 좋아요가 0인 상품에 서로 다른 사용자 100명이 동시에 좋아요를 누른다.

정상 결과:

```text
요청          100건
좋아요 성공   100건
최종 좋아요   100
```

단순하게 다음과 같이 구현하면:

```text
likeCount 조회
      ↓
likeCount + 1
      ↓
UPDATE
```

여러 트랜잭션이 동일한 값을 읽은 뒤 덮어쓰면서 Lost Update가 발생할 수 있다.

```text
기대값 : 100
실제값 : 74
```

이 문제는 인기순 조회 결과에도 직접 영향을 준다.

예를 들어 실제 좋아요가 100인데 DB에는 74로 저장된다면 인기순 정렬 역시 잘못된 데이터를 기준으로 수행된다.

## 해결 후보

- 비관적 락
- 낙관적 락
- Atomic Update

예:

```sql
UPDATE product
SET like_count = like_count + 1
WHERE id = ?;
```

동시성 제어 적용 전후를 테스트한다.

# 15. OrderItem 스냅샷

상품 정보가 수정되더라도 과거 주문 정보는 변하지 않아야 한다.

따라서 주문 시점의 상품 정보를 `OrderItem`에 저장한다.

```text
OrderItem

orderId

```

예를 들어 주문 당시 15,000원이었던 상품이 이후 18,000원으로 수정되어도 기존 주문에는 15,000원이 유지된다.

# 16. 재고 동시성 문제

본 프로젝트의 핵심 동시성 문제다.

## 상황

```text
양파 재고      100개
동시 주문      1,000건
```

정상 결과:

```text
주문 성공      100건
주문 실패      900건
최종 재고      0
```

잘못된 구현에서는 여러 요청이 같은 재고를 읽어 초과 판매가 발생할 수 있다.

## 해결 후보

- 비관적 락
- 낙관적 락
- 조건부 Atomic Update

예:

```sql
UPDATE product
SET stock = stock - :quantity
WHERE id = :productId
  AND stock >= :quantity;
```

영향받은 Row가 없다면 재고 부족으로 처리한다.

## 목표

> 실제 판매 가능한 재고보다 많은 주문이 성공하지 않아야 한다.

# 18. 결제 중복 요청 문제

사용자가 결제 버튼을 여러 번 누르거나 네트워크 재시도가 발생하면 동일 주문에 결제 요청이 여러 번 전달될 수 있다.

```text
Order #100

결제 요청 #1
결제 요청 #2
결제 요청 #3
```

실제 결제는 한 번만 처리되어야 한다.

## 고려사항

- 주문 결제 상태 확인
- 중복 결제 방지
- 요청 멱등성
- Payment / Order 상태 일관성
- 결제 실패 처리

## 목표

> 동일 주문에 같은 결제 요청이 여러 번 전달되어도 실제 결제는 한 번만 처리한다.

# 20. 주문 조회 성능 개선 - 복합 인덱스

인덱스를 처음부터 무조건 추가하지 않는다.

실제 조회 API와 쿼리를 만든 후 대량 데이터를 생성하고 실행 계획과 성능을 측정한다.

## 테스트 대상 예시

회원의 결제 완료 주문을 최신순으로 조회한다.

```sql
SELECT *
FROM orders
WHERE member_id = ?
  AND status = 'PAID'
ORDER BY created_at DESC
LIMIT 20;
```

## 테스트 흐름

```text
대량 주문 데이터 생성
        ↓
조회 실행
        ↓
실행 시간 측정
        ↓
EXPLAIN 분석
        ↓
복합 인덱스 설계
        ↓
재측정
```

후보:

```sql
CREATE INDEX idx_orders_member_status_created
ON orders(member_id, status, created_at);
```

실제 인덱스 구성은 조회 패턴과 `EXPLAIN`을 확인한 뒤 결정한다.

# 21. 인기순 조회와 인덱스 검토

인기 상품 목록은 다음과 같은 정렬을 사용한다.

```sql
SELECT *
FROM product
WHERE status = 'SELLING'
ORDER BY like_count DESC, created_at DESC
LIMIT 20;
```

상품 데이터가 충분히 많아졌을 경우 `EXPLAIN`을 통해 해당 정렬의 실행 계획을 확인한다.

필요하다면 다음과 같은 인덱스를 후보로 비교할 수 있다.

```text
(status, like_count, created_at)
```

단, 인기가 낮은 데이터 규모에서는 인덱스 추가가 오히려 불필요할 수 있으므로 **실제 측정 결과를 기준으로 적용 여부를 결정한다.**

# 22. 상품 조회 성능 개선 - Redis Cache

상품 상세는 변경보다 조회가 훨씬 많이 발생하는 데이터다.

특히 인기 상품은 다수 사용자가 같은 데이터를 반복해서 조회할 가능성이 높다.

## Cache 미적용

```text
사용자
 ↓
상품 상세
 ↓
MySQL
```

동일 상품 요청이 1,000번 들어오면 데이터베이스 조회도 반복된다.

## Cache 적용

```text
사용자
 ↓
상품 상세
 ↓
Redis

HIT
 └─ Redis에서 반환

MISS
 └─ MySQL
      ↓
    Redis 저장
      ↓
     반환
```

Spring Cache를 활용한다.

```text
@Cacheable
```

상품 수정 시에는 캐시를 제거한다.

```text
상품 수정
 ↓
DB UPDATE
 ↓
Cache Evict
```

```text
@CacheEvict
```

# 23. 인기 상품 목록 Redis Cache

메인 화면의 인기 상품 목록 역시 동일한 결과가 반복적으로 조회될 가능성이 높다.

예:

```http
GET /api/products/popular?size=10
```

매 요청마다 다음 쿼리를 실행한다면:

```text
상품 정렬
↓
좋아요 순 계산
↓
TOP 10 조회
```

DB에 반복적인 조회가 발생한다.

따라서 인기 상품 목록도 Cache 후보로 사용할 수 있다.

```text
인기 상품 요청
      ↓
Redis

HIT
 └─ 인기 상품 목록 반환

MISS
 └─ DB에서 인기순 조회
        ↓
      Redis 저장
        ↓
       반환
```

다만 좋아요 수가 계속 변경되기 때문에 너무 긴 TTL을 사용하지 않는다.

10일 프로젝트에서는 단순하게:

```text
짧은 TTL
+
필요 시 Cache Evict
```

정도로 구성한다.

### 적용 목적

> 최신성에 매우 민감한 주문·재고 데이터와 달리 인기 상품 목록은 일정 시간 정도의 지연을 허용할 수 있다고 판단하여 캐시 대상으로 선택한다.

# 37. 프로젝트에서 보여주고 싶은 핵심

본 프로젝트에서는 하나의 쇼핑몰에서 **쓰기 정합성과 읽기 성능이라는 서로 다른 백엔드 문제를 경험하고 해결한다.**

## 데이터 정합성

> 재고가 100개인데 1,000명이 동시에 주문하면 어떻게 정확히 100건만 성공시킬 것인가?

> 100명이 동시에 좋아요를 누르면 어떻게 100개의 증가를 모두 반영할 것인가?

> 동일 결제 요청이 반복되면 어떻게 중복 결제를 방지할 것인가?

## 조회 설계

> 상품명, 가격, 상태 등 다양한 조건을 어떻게 조합할 것인가?

> 같은 상품 목록에서 최신순·가격순·인기순처럼 서로 다른 정렬을 어떻게 유연하게 처리할 것인가?

## 데이터베이스 성능

> 데이터가 증가했을 때 어떤 조회가 느려지는지 어떻게 확인할 것인가?

> 실제 쿼리와 실행 계획을 기준으로 적절한 복합 인덱스를 설계할 수 있는가?

## 캐시

> 인기 상품이나 상품 상세에 반복 조회가 집중될 때 MySQL 접근을 얼마나 줄일 수 있는가?
